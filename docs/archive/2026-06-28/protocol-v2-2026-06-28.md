# UI 协议 v2 — JSON-RPC 重设计

Date: 2026-06-28

> **Status: Done** — JSON-RPC 2.0 协议已落地。`protocol/v2/`(envelope/threads/snapshot/methods)、`gateway/`(server/session/adapter/terminal/diff_review)、`frontend/src/main.js` 均已接入 v2。114 个 v2 相关测试全绿。实现偏差:v2 文件放在 `protocol/v2/` 子目录(非根);`commands.py`/`requests.py` 保留(v1 仍被 TUI 路径使用)。

## Context

voidx 桌面端尚未发布，协议可以 breaking change。现有 v1 协议有三个结构性问题：

1. **扁平事件流** — 30+ 种 `UiEvent` 平铺在一个 discriminated union 里，没有
   thread/turn 上下文。多会话场景下前端无法区分事件归属哪个会话、哪一轮。
2. **snapshot 单会话** — `TranscriptSnapshot` 只有一个 `session_id`，无法表达
   多会话状态。前端切换会话需要重新连接。
3. **自定义 envelope** — `ProtocolEnvelope` 是自研格式（`type` + `payload` +
   `seq` + `ts`），没有标准的 method/id/response 模型，前端需要手写 switch-case
   分发，无法用标准 JSON-RPC 库。

v2 采用 **JSON-RPC 2.0** 作为 wire format，引入 **Thread / Turn / Item** 三层
原语组织事件流，重新设计 command/request 为标准 method call。

### 现有协议结构（v1，将被替换）

```
ProtocolEnvelope (v1)
├── v: int = 1
├── seq: int
├── ts: float
├── type: "hello" | "snapshot" | "event" | "request" | "response" | "command"
└── payload: UiHello | TranscriptSnapshot | UiEvent | UiRequest | UiResponse | UiCommand

UiEvent = 30+ 种子类的 discriminated union（按 kind 字段区分）
UiCommand = UiSubmitCommand | UiCancelCommand（只有两种）
```

### v1 的消费端

- `frontend/src/main.js:95-117` — 前端按 `envelope.type` 分发到 snapshot/event/request
- `frontend/src/main.js:120-167` — `handleEvent()` 用 switch-case 处理 30+ 种 event.kind
- `src/voidx/ui/gateway/session.py:93-97` — 后端 `broadcast_event()` 直接发 `UiEventEnvelope`
- `src/voidx/ui/gateway/server.py:58-72` — WebSocket handler 解析 envelope 分发 command/response

## Goals and Non-Goals

### Goals

- **JSON-RPC 2.0 wire format** — 标准 method/id/response，前端可用标准库
- **Thread/Turn/Item 三层原语** — 每个事件携带 thread_id + turn_id 上下文
- **多会话原生支持** — 一个连接管理多个 thread，切换不重连
- **结构化 Item 生命周期** — started → delta → completed，替代扁平 event
- **命令统一为 method call** — session/terminal/diff/submit/cancel 都是 RPC method

### Non-Goals

- 不做 v1→v2 兼容层（桌面端未发布，直接替换）
- 批量发送支持但非必须（见下方 Batch Sending 章节，必须保证顺序）
- 不改后端 agent 执行逻辑（只改协议层和 gateway 层）
- 不改 TUI 渲染（TUI 不走 WebSocket 协议，直接消费 UiEventBus）

## Architecture

### 协议分层

```
┌─────────────────────────────────────────────────────────────┐
│  JSON-RPC 2.0 Envelope                                      │
│  {jsonrpc: "2.0", id?: int, method?: str, params?: obj,     │
│   result?: obj, error?: {code, message, data}}              │
└───────────────────────────┬─────────────────────────────────┘
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
     ┌──────────────┐ ┌───────────┐ ┌────────────┐
     │  Methods     │ │ Threads   │ │ Items      │
     │  (RPC 调用)  │ │ (会话管理) │ │ (事件流)   │
     └──────────────┘ └───────────┘ └────────────┘
```

**三种消息类型**（全部是标准 JSON-RPC）：

| 类型 | 方向 | 结构 | 用途 |
|------|------|------|------|
| **Request** | 双向 | `{jsonrpc, id, method, params}` | 前端→后端调用 method；后端→前端发起 request（权限弹窗等） |
| **Response** | 双向 | `{jsonrpc, id, result}` 或 `{jsonrpc, id, error}` | 对 Request 的回复 |
| **Notification** | 双向 | `{jsonrpc, method, params}`（无 id） | 单向事件流（Item 生命周期、Thread 状态变更） |

### Thread / Turn / Item 三层原语

```
Thread（会话）
├── thread_id: str          (= session_id)
├── title: str
├── status: "idle" | "running"
├── workspace: str
└── Turn（一轮 agent 工作）
    ├── turn_id: str
    ├── thread_id: str
    ├── status: "running" | "completed" | "cancelled"
    └── Item（原子事件，有生命周期）
        ├── item_id: str
        ├── turn_id: str
        ├── kind: str          (见下方 Item 分类)
        ├── lifecycle: "started" | "delta" | "completed"
        └── data: {...}        (kind-specific payload)
```

**设计要点**：

- **Thread** 对应一个 agent 会话，有独立的消息历史和 transcript tree
- **Turn** 对应一次 `submit` → agent 执行 → `turn.completed` 的完整循环
- **Item** 是 Turn 内的原子事件，有 `started → delta → completed` 生命周期
  （例如 `assistant_stream` item：started 创建流，delta 追加文本，completed 提交）
- 前端可以按 `thread_id` 过滤事件，按 `turn_id` 分组，按 `item_id` 聚合生命周期

### Item 分类（替代 v1 的 30+ 种 UiEvent）

v1 的 30+ 种事件按语义归并为 7 类 Item：

| Item kind | lifecycle | 对应 v1 事件 | data 字段 |
|-----------|-----------|-------------|-----------|
| `message` | started | `message.appended`, `markdown.appended`, `ansi.appended`, `thought.appended`, `warning.appended`, `error.appended`, `guidance.submitted` | `text`, `style` |

| `tool` | started → completed | `tool.started`, `tool.finished`, `tool_result.appended`, `file_change.appended` | `tool_call_id`, `label`, `args`, `elapsed`, `ok`, `detail` |

| `subagent` | started → completed | `subagent.started`, `subagent_step.started`, `subagent.finished` | `subagent_id`, `name`, `elapsed`, `ok` |

## Data Model

### JSON-RPC Envelope

```python
# protocol/v2/envelope.py

PROTOCOL_VERSION = "2.0"  # JSON-RPC 版本字符串

class JsonRpcRequest(BaseModel):
    """前端→后端 或 后端→前端的 RPC 调用"""
    jsonrpc: Literal["2.0"] = "2.0"
    id: int | str              # 请求 ID，用于匹配 response
    method: str
    params: dict[str, Any] = Field(default_factory=dict)

class JsonRpcNotification(BaseModel):
    """单向通知，无需回复（事件流、状态变更）"""
    jsonrpc: Literal["2.0"] = "2.0"
    method: str                # 无 id 字段区分 request/notification
    params: dict[str, Any] = Field(default_factory=dict)

class JsonRpcResult(BaseModel):
    """成功响应"""
    jsonrpc: Literal["2.0"] = "2.0"
    id: int | str
    result: Any

class JsonRpcError(BaseModel):
    """错误响应"""
    jsonrpc: Literal["2.0"] = "2.0"
    id: int | str | None       # None 表示 parse error 时无法匹配
    error: ErrorPayload

class ErrorPayload(BaseModel):
    code: int                  # JSON-RPC 标准错误码
    message: str
    data: dict[str, Any] | None = None

# 联合类型，用于解析入站消息
JsonRpcMessage = Annotated[
    JsonRpcRequest | JsonRpcNotification | JsonRpcResult | JsonRpcError,
    Field(discriminator=...)
]
```

**解析规则**（按字段存在性判断）：

```
有 id + method         → Request
有 method + 无 id      → Notification
有 id + result         → Result
有 id + error          → Error
有 id + 无 method/result/error → 非法
```

### Thread / Turn / Item

```python
# protocol/v2/threads.py

class ThreadInfo(BaseModel):
    thread_id: str
    title: str = ""
    workspace: str = "."
    model_provider: str = ""
    model_name: str = ""
    status: Literal["idle", "running"] = "idle"
    created_at: str = ""
    updated_at: str = ""
    message_count: int = 0

class TurnInfo(BaseModel):
    turn_id: str
    thread_id: str
    status: Literal["running", "completed", "cancelled"] = "running"
    started_at: float = 0
    elapsed: float | None = None

class Item(BaseModel):
    item_id: str
    turn_id: str
    thread_id: str
    kind: Literal[
        "message", "assistant_stream", "tool", "todo",
        "subagent", "status", "prompt",
    ]
    lifecycle: Literal["started", "delta", "completed"] = "started"
    data: dict[str, Any] = Field(default_factory=dict)
```

### Transcript Snapshot（多会话）

```python
# protocol/v2/snapshot.py

class ThreadSnapshot(BaseModel):
    """单个 thread 的 transcript 快照"""
    thread_id: str
    revision: int
    nodes: list[TranscriptNode] = Field(default_factory=list)  # 复用现有 TranscriptNode

class WorkspaceSnapshot(BaseModel):
    """连接时推送的全量快照。

    只含活跃 thread 的完整 transcript snapshot；其余 thread 只推 ThreadInfo
    元数据。前端切换到非活跃 thread 时调用 session.switch 拉取其 ThreadSnapshot。
    """
    threads: list[ThreadInfo] = Field(default_factory=list)
    active_thread_id: str = ""
    active_snapshot: ThreadSnapshot | None = None  # 仅活跃 thread 的完整 transcript
```

## API Contract

### 前端→后端 Methods

#### session 管理

| Method | Params | Result | 说明 |
|--------|--------|--------|------|
| `session.create` | `{title?}` | `ThreadInfo` | 创建新会话 |
| `session.list` | `{limit?}` | `{threads: [ThreadInfo]}` | 列出所有会话 |
| `session.switch` | `{thread_id}` | `ThreadSnapshot` | 切换活跃会话 |
| `session.fork` | `{thread_id, title?}` | `ThreadInfo` | 从现有会话 fork |
| `session.delete` | `{thread_id}` | `{ok: bool}` | 删除会话 |
| `session.rename` | `{thread_id, title}` | `{ok: bool}` | 重命名 |

#### agent 交互

| Method | Params | Result | 说明 |
|--------|--------|--------|------|
| `agent.submit` | `{thread_id, text}` | `{turn_id}` | 提交消息，启动 turn |
| `agent.cancel` | `{thread_id}` | `{ok: bool}` | 取消当前 turn |

#### terminal

> 集成终端信任用户操作，不限制可执行命令。终端在用户 workspace 下运行，
> 所有命令（包括危险操作）由用户自行负责，后端不做命令过滤或拦截。

| Method | Params | Result | 说明 |
|--------|--------|--------|------|
| `terminal.start` | `{thread_id, cwd?}` | `{terminal_id}` | 启动终端 |
| `terminal.input` | `{terminal_id, data}` | `{ok: bool}` | 写入终端 |
| `terminal.resize` | `{terminal_id, cols, rows}` | `{ok: bool}` | 调整大小 |
| `terminal.stop` | `{terminal_id}` | `{ok: bool}` | 关闭终端 |

#### diff review

> Hunk 重建仅处理文本文件，二进制文件跳过 hunk 级 review（直接显示
> "binary file changed"）。diff review 状态保持在内存中，不持久化。

| Method | Params | Result | 说明 |
|--------|--------|--------|------|
| `diff.review` | `{thread_id}` | `{review_id, file_diffs}` | 生成 diff review（文本文件含 hunk，二进制文件标记跳过） |
| `diff.decide` | `{review_id, decisions}` | `{ok: bool}` | 提交 hunk 决策（accept/reject per hunk） |
| `diff.apply` | `{review_id}` | `{files_changed: [str]}` | 应用已 accept 的 hunk |

### JSON-RPC 错误码

| Code | 含义 | 场景 |
|------|------|------|
| `-32700` | Parse error | JSON 解析失败 |
| `-32600` | Invalid request | 不是合法的 JSON-RPC 消息 |
| `-32601` | Method not found | 未知 method |
| `-32602` | Invalid params | 参数缺失或类型错误 |
| `-32603` | Internal error | 后端执行异常 |
| `-32000` | Thread not found | session_id 不存在 |
| `-32001` | Turn in progress | 会话正在运行，无法切换 |
| `-32002` | Terminal not found | terminal_id 不存在 |

### 连接握手

```
前端                              后端
  │
  ├─ Request: hello ────────────►  {id: 1, method: "hello", params: {client: "desktop"}}
  │                                ├─ 验证 client
  │                                ├─ 构建 WorkspaceSnapshot（所有 thread + 活跃 thread 快照）
  │◄─── Result: snapshot ────────  {id: 1, result: WorkspaceSnapshot}
  │
  │  （后续前端按需调用 session.switch / agent.submit 等）
  │
  ├─ Notification: item.delta ──►  （后端持续推送事件流）
  │◄─── Notification: item.delta ─
  │
  ├─ Request: permission.prompt ◄──  {id: 2, method: "permission.prompt", params: {...}}
  ├─ Result: {value: "allow"} ───►  {id: 2, result: {value: "allow"}}
```

### UiEvent → Item 转换层

gateway 层新增 `UiEventItemAdapter`，将现有 `UiEvent` 转换为 `Item` notification：

```python
# src/voidx/ui/gateway/adapter.py

class UiEventItemAdapter:
    """将 UiEventBus 事件转换为 v2 Item notifications。"""

    def __init__(self, thread_id: str, turn_id: str) -> None:
        self._thread_id = thread_id
        self._turn_id = turn_id
        self._item_ids: dict[str, str] = {}  # v1 关键标识 → item_id

    async def handle(self, event: UiEvent) -> JsonRpcNotification | None:
        """UiEvent → Item notification。返回 None 表示该事件不映射为 Item。"""
        # tool.started → item.started (kind="tool")
        # tool.finished → item.completed (kind="tool")
        # assistant_stream.updated → item.delta (kind="assistant_stream")
        # todo.updated → item.started (kind="todo", 每次 full replace)
        # ...
```

**设计理由**：agent 核心逻辑（`run_loop.py`、`UiEventBus`）完全不动，
只在 gateway 层做 UiEvent→Item 的适配转换。这样协议升级的影响面控制在
`ui/protocol/` + `ui/gateway/` + `frontend/`，不触及 agent 核心。

## Error Handling

| 失败场景 | 处理策略 |
|---------|---------|
| JSON 解析失败 | 返回 `{jsonrpc: "2.0", id: null, error: {code: -32700, message: "parse error"}}` |
| 未知 method | 返回 `{error: {code: -32601, message: "method not found"}}` |
| 参数校验失败 | 返回 `{error: {code: -32602, message: "invalid params", data: {field: ...}}}` |
| 会话切换时 turn 运行中 | 返回 `{error: {code: -32001, message: "turn in progress"}}`，前端提示等待 |
| thread_id 不存在 | 返回 `{error: {code: -32000, message: "thread not found"}}` |
| 前端未回复 request 超时 | 后端 30s 超时后按 "cancel" 处理 |
| WebSocket 断连 | 前端自动重连，重连后发 `hello` 获取全量 snapshot |
| 后端内部异常 | 返回 `{error: {code: -32603, message: "internal error", data: {detail: ...}}}` |

## Decisions Log

| 决策 | 备选方案 | 选择理由 |
|------|---------|---------|
| JSON-RPC 2.0 而非自定义 envelope | 保留 v1 的 type+payload 格式 | JSON-RPC 是标准，前端可用标准库，method/id 模型天然支持 RPC |
| Item 用 lifecycle 而非独立事件 | 保留 v1 的 started/updated/finished 三种事件 | lifecycle 字段让前端按 item_id 聚合，减少事件种类 |
| 30+ UiEvent 归并为 7 类 Item | 保留全部 30+ 种 | 减少前端 switch-case 复杂度，语义更清晰 |
| UiEvent→Item 转换在 gateway 层 | 在 agent 核心层直接发 Item | agent 核心不感知协议版本，协议升级不影响 agent 逻辑 |
| Thread = session 而非新概念 | 引入独立 Thread 实体 | session 已有完整 CRUD + 持久化，复用避免重复 |
| notification 无 id | 所有消息都有 id | JSON-RPC 标准：无 id = notification，无需回复，减少往返 |
| 多会话共享一个 WebSocket | 每会话独立连接 | 单连接 + thread_id 路由更高效，前端管理简单 |
| TranscriptNode 不变 | 重新设计 node 结构 | node 结构与协议无关，是 UI 渲染单元，改动无收益 |
| `item.delta` data 用 full-replace | incremental patch | 简单优先，前端覆盖渲染，无需维护 patch 逻辑 |
| 多会话并行不限制 turn 数量 | 后端限流 | 共享 LLM provider 速率限制，信任 provider 侧 429 自然调节 |
| permission 超时固定 30s | 可配置超时 | 保持简单，不暴露配置项 |
| terminal 不做背压 | gateway 层 output coalescing | xterm.js 自身有渲染缓冲，实际卡顿再加 |
| WorkspaceSnapshot 只推活跃 thread | 推所有 thread 完整 transcript | 避免大会话列表时 snapshot 过大，非活跃 thread 按需拉取 |
| Item envelope 支持批量发送 | 逐个发送 | 减少 WebSocket 帧数，但必须保证数组内顺序 |

## Resolved Questions

- [x] **`item.delta` 的 `data` 语义** — full-replace。`data` 始终是当前完整状态，
      前端覆盖渲染。assistant_stream 的 `data.text` 是累积全文，不是增量片段。
      理由：简单优先，前端无需维护 patch 逻辑。省带宽是后续优化。
- [x] **多会话并行时是否限制同时运行的 turn 数量** — 不限制。多会话并行时共享
      LLM provider 的速率限制，后端不额外限制同时运行的 turn 数量。信任 provider
      侧的 429/限流机制自然调节。
- [x] **`permission.prompt` 等 request 超时时长是否可配置** — 固定 30s 超时，
      超时后按 "cancel" 处理。不暴露配置项，保持简单。后续如有需求再加。
- [x] **terminal PTY 输出背压控制** — 暂不做背压。高频输出时前端 xterm.js 自身
      有渲染缓冲。如果实际出现卡顿，后续在 gateway 层加 output coalescing
      （合并短时间内的多个 `terminal.output` notification）。
- [x] **`WorkspaceSnapshot` 大小问题** — 只推活跃 thread 的完整 snapshot，
      其余 thread 只推 `ThreadInfo`（元数据，不含 transcript nodes）。
      前端切换到非活跃 thread 时调用 `session.switch` 拉取该 thread 的
      `ThreadSnapshot`。

## Batch Sending

Item envelope 支持批量发送，但必须保证顺序。

**设计**：后端可以将多个 notification 合并到一个 JSON 数组中一次性发送：

```json
[
  {"jsonrpc": "2.0", "method": "item.started", "params": {...}},
  {"jsonrpc": "2.0", "method": "item.delta", "params": {...}},
  {"jsonrpc": "2.0", "method": "item.completed", "params": {...}}
]
```

**规则**：
- 批量消息是 JSON 数组，每个元素是标准的 `JsonRpcNotification`
- 数组内元素的顺序就是事件发生的顺序，前端必须按数组顺序处理
- 前端处理完一个批次后才处理下一个批次（不跨批次并行）
- 单个 notification 仍然可以单独发送（不强制批量）
- Request/Response 不参与批量（每个都有独立 id，需单独匹配）

**使用场景**：agent 一步操作产生多个事件时（如 tool.started + tool.finished
在快速完成时），gateway 可以合并为一个批次减少 WebSocket 帧数。
