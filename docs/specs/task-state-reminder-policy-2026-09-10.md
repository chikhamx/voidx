# Task State 按需更新与周期提醒策略

- 日期：2026-09-10
- 状态：策略已确认，待实现；本文不表示运行时代码已具备此策略。
- 适用范围：所有启用 Current Task State 的主 agent 与 subagent；统一内置启用，不提供用户开关。
- 现有实验实现参考（由本 spec 取代其开关设计）：[Task-state history cache experiment](../design/task-state-cache-experiment.md)。

## 1. 问题与目标

当前保留模式在每次模型调用时追加完整 Task State，并保留之前实际发送的快照。这避免主动删除历史状态消息，但在状态长期不变时产生大量重复内容。

目标是在不重写旧快照的前提下，兼顾状态提醒与上下文成本：状态发生实质变化时立即更新；没有变化时按调用次数或新增上下文量周期提醒。模型需要持续看到当前目标与下一步，而不是每次读取相同的完整状态。

缓存命中受上游路由、协议实现及其他前缀变化影响。本策略不承诺逐次命中或解决所有缓存异常。

## 2. 内置策略与实验开关退场

本策略成为所有启用 Current Task State 的 agent 的默认行为：保留已发送快照，只在需要时追加。用户不需要输入命令启用，也不需要管理清理模式。

实现时移除 `/taskstate` 注册、选择菜单、帮助项、状态命令及对应 slash 专用接口，删除运行时 strip 开关分支，更新命令契约快照和实验说明。复用快照保留能力，不保留一个隐藏的旧清理开关，也不新增策略选择命令。移除命令与统一策略必须在同一变更内完成，不能先移除开关却仍每轮追加。

策略阈值集中定义，默认分别为 5 次成功模型调用和 8,192 个估算新增输入 tokens。初期无需扩展持久化设置或前端设置页；诊断信息通过已有日志和 context frame 元数据查看。

内置 chat 模式主动抑制 Current Task State，本策略不得绕过该限制。主 agent 与每个 subagent 分别按自身 prompt policy 判断是否参与；不能因为父会话是 chat 就一律禁用子代理状态，也不能因为父会话启用就向主动抑制该段落的子代理注入。

## 3. 触发规则

在每次实际请求准备阶段评估以下条件，任意一个成立就追加一份最新、完整且精简的快照。一次请求最多追加一份。

| 条件 | 原因标记 | 行为 |
|---|---|---|
| 当前运行会话还没有成功发送的快照 | `initial` | 追加初始快照 |
| 上下文压缩、裁剪或历史重写，使已记录的快照锚点不再有效 | `history_reset` | 在新历史上追加最新快照，建立新计数基线 |
| 新的真实用户输入已进入当前请求 | `user_message` | 即使状态相同，也追加一次提醒 |
| 规范化状态指纹与最近成功快照不同 | `state_changed` | 立即追加最新快照 |
| 距上次成功快照已有 5 次成功模型调用未发送快照 | `call_interval` | 追加周期提醒 |
| 相对上次成功快照，新增语义输入达到 8,192 个估算 tokens | `token_interval` | 提前追加周期提醒 |
| 以上均不成立 | `unchanged` | 不生成新的状态消息；仍恢复已有快照 |

多个条件同时成立时按表内顺序选择主要原因，诊断信息可以同时记录其他命中条件。只追加一次，只重置一次基线。

真实用户输入包括被接纳的用户中途补充消息；工具结果、内部 guidance、压力提醒和 Task State 自身不算用户输入。使用现有输入事件标识或消息 ID 判断是否为新输入，不根据 `role=user` 或文本内容判断。subagent 新收到的明确任务补充另用 `task_message` 标记，语义见第 7 节；其优先级与 `user_message` 相同。

## 4. 计数的精确定义

### 成功调用次数

`calls_since_snapshot` 表示最近一次成功发送快照之后，未携带新快照而成功完成的逻辑模型调用次数。

- 携带新快照的请求成功：置为 0。
- 未携带新快照的请求成功：加 1。
- 请求失败、传输重试、上下文预构建、token 估算：不计数。
- 一次流式请求的多个 chunk 不分别计数。
- 模型成功返回工具调用也算一次成功调用。
- 中止或没有被运行时接受的部分响应不提交策略状态。

默认时序如下，假设没有其他触发条件：

| 请求 | 请求前计数 | 是否追加快照 | 成功后的计数 |
|---|---:|---|---:|
| 1 | 无基线 | 是，初始快照 | 0 |
| 2～6 | 0～4 | 否 | 1～5 |
| 7 | 5 | 是，周期提醒 | 0 |

这一定义避免“每 5 次”出现不同实现。次数阈值不是模型记忆能力的保证，后续根据测试结果调整。

### 新增上下文 tokens

只估算自最近成功快照以来新进入请求的语义消息内容，包括 assistant 输出、工具调用及结果、用户消息。使用运行时现有的同模型 token 估算器。

- 不使用上游 `input_tokens` 累加；否则重复发送的整段历史会被重复计算。
- 排除系统指令、工具定义和所有 Task State 快照；它们不属于此计数的新增语义内容。
- 在历史保持追加的情况下，取当前语义输入估算量减去最近成功快照请求的语义输入估算量。
- 把本次请求新加入的工具结果计入，因此一个很大的工具结果可以立即触发提醒，不必再等一次模型调用。
- 同一请求的多次构建或重试得到同一基线下的估算，不累加。
- 发生历史重写时不继续使用旧差值，也不靠负数截断掩盖变化；转入 `history_reset` 并在成功后更新基线。

token 阈值表示估算量，不要求与上游 tokenizer 或计费 tokens 完全一致。

## 5. 状态内容与指纹

最新快照必须能独立表达当前状态，不要求模型把若干历史差量拼接起来。

保留具有实际决策价值的信息：当前目标、当前 persona/执行阶段、活跃计划或 workflow 节点、正在进行的关键步骤、阻塞项，以及已有结构化状态中的下一步。没有的数据不编造。

减少重复：

- 不包含刷新时间、采样时间、调用计数和周期提醒计数。
- 排除纯展示动画、无语义变化的排序抖动及重复工具日志。
- 不复制大段工具结果、已完成的全部任务清单或系统指令。
- 工具成功本身不算状态变化；目标、待办状态、阻塞项等发生实质改变才算。
- 有语义的顺序变化不得为了指纹稳定而忽略。

先从结构化状态提取快照数据，再规范化、计算指纹和渲染文本。指纹与渲染使用同一份规范化数据，避免“指纹没变但显示内容变了”。周期提醒使用相同内容，不在消息正文添加递增序号或当前时间。

本期优先复用现有状态渲染，去除不影响决策的高频动态字段。不得为了压缩快照静默截断目标或关键约束。若快照偏长，记录诊断数据后再调整字段范围，不在本期引入额外模型调用做摘要。

在稳定指令中仅说明一次：历史 Task State 是当时的快照，最后一份为最近已知状态；更新的真实用户指令和工具事实仍然有效。快照不能提高自身指令优先级，也不能覆盖新的用户要求。

## 6. 历史与请求生命周期

保留旧快照的文本、角色和位置，不在日常请求中修改、移动或删除。无更新时直接使用已有历史，不追加“状态同上”之类的占位 user 消息。

策略评估分为两个阶段：

1. **准备**：根据当前语义历史、状态和已提交基线，产生是否追加及触发原因。这个阶段不修改计数、不提交指纹。
2. **提交**：逻辑模型请求成功且被运行时接受后，记住本次实际发送的快照、指纹、用户输入标识与计数基线；未发送新快照则只更新成功调用次数。

网络重试不得提前消耗提醒额度。若失败期间状态真的发生变化，下次请求可以重新准备最新快照，但只提交最终成功发送的一份。一次请求内部的重复渲染不产生重复快照。

上下文压缩可以合并历史状态。压缩后只在新历史上补一份最新完整快照，不能从保留缓存里恢复已被压缩掉的旧状态。历史锚点失效时复用现有快照裁剪机制，并强制重新提醒。

各会话或 agent run 独立持有运行态。新会话、新子代理 run 或进程重启时从初始状态开始；切换到抑制 Current Task State 的 profile 时清空该上下文的提醒运行态，重新启用该段落时建立新基线。切换模型时重置提醒基线，避免沿用另一模型的 token 估算；不保证跨模型缓存复用。不得把上一个会话或 run 的快照带到另一个上下文。

## 7. Subagent 生命周期与隔离

主 agent 和 subagent 必须使用同一个策略实现及默认阈值，但不共享可变状态。策略实例归属具体对话上下文：主会话使用其会话身份，子代理使用所属会话与稳定的 agent run 身份，不能只用显示名称作为键。并行及嵌套子代理同样隔离。

- **启动**：子代理首次实际请求发送其自己的精简快照，描述受委派目标、当前步骤、阻塞项及已有下一步。不复制父代理整份 Task State 或父代理的历史快照。
- **工具循环**：每次成功模型调用独立计数，按本 run 的新增上下文计算 token 阈值。工具执行次数、父代理调用次数、其他子代理的活动均不累计到本 run。
- **任务补充**：新的父代理指令、用户转交指令或明确改变工作要求的消息被接纳进本 run 后，触发 `task_message`。对同一消息去重；状态轮询、送达确认和内部心跳不触发。普通结果消息按状态变化或 token 增量规则处理，不一律当作新用户消息。
- **暂停与恢复**：同一运行进程中，同一 run 保留了相同语义历史时继续使用原基线。重新构造上下文、重启进程或新建 run 时重新建立基线并提醒；不得从父代理基线推导。
- **重试、压缩与失败**：与主 agent 使用同一准备／提交规则。失败重试不消耗额度，压缩后不复活已移除快照。
- **结束与取消**：不为了满足提醒间隔额外调用模型；释放已结束 run 的提醒运行态。若之后重新启动工作，按实际 run 生命周期决定恢复或初始化，不根据复用的显示名称恢复旧状态。
- **父代理反馈**：子代理完成可能改变父代理自己的结构化任务状态，父代理因此触发 `state_changed`；不能把子代理的快照、指纹或计数合并进父代理。

策略层不得依赖全局 singleton 或 execution host 上未区分 run 的共享计数。共享阈值是允许的，共享快照容器和提交状态是不允许的。

## 8. 实现落点

- `agent/application/task_state_history.py`：保留已发送快照、恢复位置，提供锚点有效性信息。
- 新增职责独立的提醒策略模块：用结构化类型保存阈值、提交状态和准备决策；不依赖 presentation 或具体模型 SDK。
- `agent/application/runtime_context.py`：支持“恢复已有快照，但本次不追加”的构建路径；不再保留按开关选择每轮清理的路径。
- `agent/adapters/langgraph/runtime/llm_turn.py`：在实际请求准备时评估策略，在成功响应被接受后提交。
- `agent/adapters/langgraph/runtime/subagent.py`：接入同一策略，在子代理请求构建和成功响应处理处评估／提交，不仅修改主 agent 路径。
- 子代理 gateway／runner：负责 run 级策略生命周期与隔离；具体归属应贴合现有执行上下文，不把所有子代理挂到父 host 的同一个 history 实例。
- 现有 slash 接口及命令契约：移除实验 `/taskstate` 的注册与专用适配层；日志不依赖 slash 状态查询。

快照和策略状态继续只在运行内存维护，不写入真实用户聊天记录。首次实现必须覆盖主 agent 和 subagent；不包含原生 Responses provider、中转站补丁或缓存 TTL 调整。

## 9. 可观测性

在已有诊断日志或 context frame 元数据中记录，不插入模型提示词：

- 所属会话／agent run 身份、本次是否追加、触发原因。
- 状态指纹、距上次快照的成功调用数、估算新增 tokens。
- 本次快照估算 tokens、已保留快照数量、锚点是否重置。

复用现有 usage 统计观察缓存读取和总输入，不把缓存命中作为策略触发器，以免路由波动导致提示词本身随之抖动。

## 10. 验收标准

1. 支持 Current Task State 的主 agent 和 subagent 默认应用该策略；`/taskstate` 及其清理开关完全移除；chat 等抑制该段落的 profile 仍不注入。
2. 初次请求发送一份快照；状态不变、未达阈值时不追加任何状态占位消息。
3. 达到第 4 节定义的次数阈值时，下一次请求恰好追加一份；其他触发同时成立也不重复。
4. 一条新增大工具结果使估算增量达到 8,192 tokens 时，本次请求立即提醒；低于阈值时不提前提醒。
5. 目标、待办、阻塞项等实质变化立即更新；只有采样时间变化不更新。
6. 新真实用户输入只触发一次，后续工具循环不会再次把同一输入当成新消息。
7. 请求重建、失败、重试不改变已提交计数和快照数量；重试成功后只提交一次。
8. 无状态更新的多次工具循环与有状态更新的循环，都保持旧快照内容和位置；未更新时没有额外 user 消息。
9. 压缩、会话／run 切换、模型切换及 profile 抑制正确重置，不恢复失效快照。
10. 主 agent 与至少两个并行 subagent 的快照、计数和 token 基线互不影响；嵌套子代理遵守相同隔离规则。
11. 子代理首次调用、工具循环、任务补充去重、失败重试、压缩、暂停恢复及结束清理均有集成测试。
12. 父代理接收子代理结果时只更新自身状态，不合并子代理的快照或提醒计数；抑制规则按每个 agent 自己的 profile 生效。
13. 通过独立单元测试、主／子代理实际请求构建集成测试，以及命令移除契约和相关架构检查。

效果验证采用相同 provider、模型和 effort 的独立新会话，分别对主 agent 与 subagent，对比当前实验版本“每次追加”与本策略；通过测试夹具或两个版本完成对照，不为此保留生产命令开关。记录快照次数和 tokens、总输入、工具循环内的缓存读取，以及实际任务是否出现遗漏、重复执行或依据旧状态行动。减少重复快照是可确定的验收指标；缓存改善和任务质量必须实测，不预先承诺。
