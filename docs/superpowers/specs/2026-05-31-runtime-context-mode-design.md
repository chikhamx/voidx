# Runtime Context and Mode Design

Date: 2026-05-31

## Goal

Refactor voidx runtime context assembly and mode handling so the LLM sees a stable, structured context, while UI/session/permission state stay explicit and testable.

This design keeps the current event-bus UI direction and avoids turning "mode" into one overloaded enum. Mode is split into interaction intent, permission profile, execution policy, agent role, and UI state.

## Current State

Key files:

- `src/voidx/config.py` defines `SandboxMode`, `ApprovalPolicy`, and `PermissionMode`.
- `src/voidx/permission/service.py` applies permission presets and session allow/deny rules.
- `src/voidx/agent/graph.py` builds the LangGraph and injects system content by appending strings to the first `SystemMessage`.
- `src/voidx/agent/state.py` carries `plan_mode: bool`.
- `src/voidx/agent/slash.py` toggles `/plan` and `/unplan` directly through `_g._plan_mode`.
- `src/voidx/agent/graph_parts/run_loop.py` builds the per-turn `AgentState`, loads session messages, restores transcript snapshots, and emits startup/status events.
- `src/voidx/llm/instruction.py` loads AGENTS/CLAUDE instructions and active skill instructions.

Observed gaps:

- `plan_mode` is a boolean, but the product needs a clearer user-facing mode contract.
- `PermissionMode.AUTO_REVIEW` currently maps to `approval_policy=on-failure`, which is not the same concept as a reviewer deciding approval prompts.
- Context is assembled through string appends into `SystemMessage`, so source, priority, and section boundaries are hard to test.
- Skills are injected into the same system string as project instructions, making active skill state hard to distinguish from permanent facts.
- UI status reads `plan_mode` only, so users cannot see a coherent view of interaction mode, permission profile, sandbox, approval behavior, and agent role.
- Session transcript restoration is UI state; it should remain separate from LLM context construction.

## Runtime Context Shape

Build the LLM prompt from named sections in this order:

1. Base System
2. Role Prompt
3. Tool Contract
4. Workspace Facts
5. Project Facts
6. Architectural Decisions
7. Long Summary
8. Current Date
9. Runtime State
10. Recent Messages
11. Active Skills
12. Current Task State
13. User Message

Section responsibilities:

- Base System: stable voidx behavior rules, communication style, global tool-use rules, and common constraints.
- Role Prompt: current execution role instructions (`orchestrator|explore|plan|implement|review`).
- Tool Contract: current role write/delegation permissions, tool allowlist, and step budget.
- Workspace Facts: workspace path, repo status facts, configured MCP/LSP availability, and instruction files loaded.
- Project Facts: durable facts about this project that are not tied to one task.
- Architectural Decisions: durable decisions with rationale and scope.
- Long Summary: compacted history summary generated by compaction.
- Current Date: current wall-clock date/time for this turn, kept out of the runtime envelope so its position is explicit and easy to test.
- Runtime State: workspace, provider/model, interaction mode, permission profile, sandbox mode, approval policy, approval reviewer, and current execution gates. Internal ids such as `agent_id` stay in metadata, not prompt text.
- Recent Messages: unmodified recent conversation tail.
- Active Skills: loaded skill ids, descriptions, and full instructions only for active matched skills.
- Current Task State: mode, goal, plan/todo state, active files, known constraints, blockers, and next action.
- User Message: the current user turn, including structured attachments.

Active Skills intentionally sit after Recent Messages and before Current Task State. This makes skills salient for the immediate task without incorrectly promoting them into project memory.

## Mode Model

Use multiple axes instead of one mode enum.

### InteractionMode

User-facing execution strategy:

- `auto`: infer the per-turn task intent from user input.
- `plan`: read-only exploration and implementation planning.
- `goal`: keep multi-step work scoped to the current goal.

This replaces `_plan_mode: bool` as the user-facing task mode. `plan_mode` can remain as a compatibility property during migration.

### TaskState

`InteractionMode` is the user-visible contract, while `TaskIntent` remains the internal per-turn classifier (`chat|inspect|design|review|implement|debug|ambiguous`). `TaskState` tracks short-lived multi-turn intent:

- `current_intent`
- `previous_intent`
- `current_goal`
- `awaiting_implementation_approval`
- `approved_scope`
- `last_plan_summary`

The intent resolver should treat approval phrases such as "可以" or "对，可以" as implementation approval only when `awaiting_implementation_approval=true`. A direct implementation request such as "开始实现" or "直接改" can enter `implement` without a pending plan. Non-design turns clear pending approval, so a stale "可以" does not accidentally start editing an old scope.

### PermissionProfile

User-facing preset:

- `default`: workspace-write sandbox, ask for risky tools.
- `read-only`: read-only sandbox, no writes or implement delegation.
- `accept-edits`: allow file edits in workspace, still ask for unsafe bash/network/out-of-workspace actions.
- `auto-review`: use an approval reviewer for permission prompts where possible.
- `full-access`: danger-full-access plus no prompts.
- `custom`: explicit sandbox/approval settings from config.

### ExecutionPolicy

Low-level enforcement:

- `sandbox_mode`: `read-only`, `workspace-write`, `danger-full-access`.
- `approval_policy`: `untrusted`, `on-request`, `never`.
- `approval_reviewer`: `user` or `auto_review`.
- `extra_write_paths`: explicit workspace-write additions.

`on-failure` should be treated as a legacy compatibility option. The preferred model is explicit reviewer behavior plus sandbox.

### WorkerRole

Execution identity:

- `orchestrator`
- `explore`
- `plan`
- `implement`
- `review`
- `compaction`
- `title`

The primary orchestrator keeps `agent_id=-1`. Worker role runs keep numbered ids from `0` upward for UI/event correlation.

Prompt text uses semantic role names and task scopes, not internal ids. `agent_id`, parent ids, tool call ids, and frame ids are persisted as metadata for UI/debug correlation only.

### UiMode

TUI state, not generally LLM context:

- `input`
- `command_palette`
- `permission_prompt`
- `text_prompt`
- `transcript_viewer`
- `review_panel`
- `background_task`

UiMode enters LLM context only when it changes the current task contract.

## Data Flow

Per user turn:

1. Run loop receives input and builds the structured user payload.
2. Session store loads persisted semantic messages, not transcript-only UI rows.
3. Context builder discovers instruction files, active skills, summary, task state, role prompt, tool contract, and runtime state.
4. Context builder emits:
   - one system message containing the stable prefix and dynamic runtime sections;
   - recent conversation messages as native LangChain messages;
   - a final user message for the current turn.
5. Graph nodes operate on this assembled context.
6. UI receives serialized events through `ui_events`; transcript snapshot remains separate from LLM context.

## Slash Commands

Initial command surface:

- `/mode`: show or choose `auto|plan|goal`.
- `/plan`: compatibility alias for `/mode plan`.
- `/unplan`: compatibility alias for `/mode auto`.
- `/goal <text>`: set the current goal and enter goal mode.
- `/goal clear`: clear the current goal and return to auto mode.

Goal mode uses a structured `TaskRun` that is persisted with the session:

- `goal`
- `phase`: `clarify|inspect|design|implement|verify|review|done`
- `status`: `idle|active|done`
- `approved_scope`
- `awaiting_implementation_approval`
- `turn_count`

If `/mode goal` is selected without an existing goal, the next user message becomes the goal. Goal mode does not grant write permission by itself; implementation still requires explicit implementation intent or confirmation of a pending plan.
- `/permission-mode`: continue to control permission profile.

Mode changes should update UI status and Current Task State.

## Session Persistence

Runtime/session state is stored structurally rather than as one opaque JSON blob:

- `session_runtime_state`: current `InteractionMode` and `TaskState`.
- `session_task_runs`: current goal run, phase, approval scope, and turn count.
- `message_runtime_snapshots`: per-user-message mode, resolved intent, implementation gate, and goal snapshot.
- `context_frames`: compiled LLM messages before each call, plus `prefix_hash`, `frame_hash`, token estimate, frame kind, and metadata.

`/resume` hydrates these tables before replaying the startup/transcript UI, so restored context and UI status match the previous session contract. `/clear` and `/goal clear` reset the structured runtime state in the same place instead of only clearing visible transcript rows.

## Permission Changes

Recommended migration:

- Keep existing config values backward compatible.
- Add `PermissionMode.READ_ONLY` and `PermissionMode.ACCEPT_EDITS`.
- Rework `PermissionMode.AUTO_REVIEW` to mean `approval_reviewer=auto_review`, not `approval_policy=on-failure`.
- Keep `ApprovalPolicy.ON_FAILURE` parseable for existing configs, but mark it legacy in labels/docs.
- Apply write restrictions from either `InteractionMode.plan` or `ExecutionPolicy.sandbox_mode=read-only`.

## UI Changes

Footer/detail panel should show:

- interaction mode;
- permission profile;
- sandbox label;
- approval policy;
- approval reviewer;
- current agent/status;
- context usage.

Prompt/status events should use the existing event bus. Startup/transcript rendering stays as UI events and does not become part of LLM context.

## Error Handling

- Unknown mode strings are rejected with a UI error.
- Unknown permission profiles fall back to `custom`.
- If active skill loading fails, context builder records a warning section and continues.
- If compaction summary is unavailable, omit Long Summary instead of inserting empty headers.
- If session restore has no semantic messages, startup still renders normally and Recent Messages is empty.

## Testing

Add focused tests:

- context section ordering and rendering;
- Active Skills placement after Recent Messages and before Current Task State;
- `/mode` command transitions and `/plan` compatibility;
- `plan` mode denies write/edit/bash/lsp_format and implement subagent delegation;
- permission profile defaults for `read-only`, `accept-edits`, `auto-review`, and `full-access`;
- UI footer/detail panel includes interaction mode and approval reviewer;
- transcript restore does not alter context builder inputs.

Run full tests after implementation:

```bash
.venv/bin/python -m pytest tests/ -v
```
